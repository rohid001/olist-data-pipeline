# Olist Data Pipeline Architecture

A monthly batch ELT pipeline: the Olist data is split into monthly batches, loaded as-is into the `raw`
schema, then cleaned and modelled by dbt up to the `marts` schema that Power BI reads. Every number in
this document comes from `docs/data_profile.md` (generated by `python -m ingestion.profile_data`).

## 1. Layers and schemas

| Schema | Contents | Built by | Materialization |
| --- | --- | --- | --- |
| `raw` | Copy of the CSV files: every business column stored as `TEXT`, plus 3 metadata columns | `ingestion/load_raw.py` | table |
| `staging` | One model per source table: rename columns, cast data types, deduplicate reviews | dbt | view |
| `intermediate` | Logic reused by more than one mart | dbt | view |
| `marts` | Dimension, fact, and analytics tables for Power BI | dbt | table; `fct_orders` is incremental |

## 2. Naming conventions

- Tables in `raw` use the names from the data contract: `orders`, `order_items`, `order_payments`,
  `order_reviews`, `customers`, `products`, `sellers`, `geolocation`.
- dbt models: `stg_<table>`, `int_<topic>`, `dim_<entity>`, `fct_<process>`, `mart_<topic>`.
- Metadata columns start with an underscore: `_batch_id` (`YYYY-MM` or `static`), `_source_file`,
  `_loaded_at`.
- Business column names stay as in the source (`order_id`, `customer_state`, ...) so they match the
  Olist documentation and the original Data Analyst project.

## 3. Source table contract

The version used by the pipeline is the code in `ingestion/data_contract.py`. The values in the
*Monthly partition* and *Load strategy* columns are exactly the `partition_type` and `load_strategy`
values in the code.

| Table | Grain (unique key) | Monthly partition | Load strategy | Reason |
| --- | --- | --- | --- | --- |
| orders | `order_id` | `time_column`: `order_purchase_timestamp` | `delete_insert` | Every order belongs to exactly one month |
| order_items | `order_id` + `order_item_id` | `parent_table`: orders | `delete_insert` | Items have no transaction date of their own |
| order_payments | `order_id` + `payment_sequential` | `parent_table`: orders | `delete_insert` | Payments have no date of their own |
| order_reviews | `review_id` + `order_id` | `time_column`: `review_creation_date` | `delete_insert` | A review only exists once it is created; `review_id` alone has 814 duplicates |
| customers | `customer_id` | `parent_table`: orders | `delete_insert` | `customer_id` maps 1:1 to an order (0 reused) |
| products | `product_id` | `parent_table`: order_items | `upsert` | 11,869 of 32,951 products sold in more than one month |
| sellers | `seller_id` | `parent_table`: order_items | `upsert` | 2,344 of 3,095 sellers sold in more than one month |
| geolocation | none | `static` | `full_replace` | Reference data; 261,831 fully duplicated rows |
| product_category_name_translation | `product_category_name` | `dbt_seed` | `dbt_seed` | 71 official rows + 2 manual translations from the DA project, versioned in Git |

## 4. Monthly batches

- 26 batches, `2016-09` to `2018-10`. One Airflow run processes one batch.
- A month without data is still a **successful** run with 0 rows: `2016-11` has no orders (but 101
  reviews); `2016-09`, `2018-09`, and `2018-10` have no reviews.

## 5. Idempotency rules

1. One batch is loaded in **one transaction**: either every table in the batch succeeds, or nothing
   changes.
2. `delete_insert`: `DELETE ... WHERE _batch_id = '<batch>'`, then `INSERT` the rows of that batch.
3. `upsert`: `INSERT ... ON CONFLICT (<key>) DO UPDATE`. This is why `raw.products` and `raw.sellers`
   must have a `PRIMARY KEY`.v
4. `full_replace`: `TRUNCATE`, then `INSERT`.
5. Proof required: loading the same batch twice gives exactly the same row counts in every table
   (checked after the first load and again with an Airflow rerun).

## 6. Data types in `raw`

Every business column is stored as `TEXT`. Loading never fails because of a date or number format;
type casting happens once in `staging` and is tested by dbt. This follows the same principle as the
DA project: load and audit first, constrain later.

## 7. Late-arriving data and anomalies

- 40,967 of 99,224 reviews (41.3%) are created in a later month than their order. Marts that use
  reviews are fully rebuilt (`table` materialization) instead of being incremental by order month.
- 33 reviews are created in a month **before** their order. This is a dbt test with severity `warn`:
  it is reported but does not stop the pipeline.
- The dataset only contains the final status of each order, so the monthly batches are a *replay* of
  history, not real changes to the data.

## 8. Grain of the mart models

| Model | Grain |
| --- | --- |
| `fct_orders` | 1 row per `order_id` |
| `fct_order_items` | 1 row per `order_id` + `order_item_id` |
| `dim_customers` | 1 row per `customer_unique_id` |
| `dim_products` | 1 row per `product_id` |
| `dim_sellers` | 1 row per `seller_id` |
| `mart_customer_rfm`, `mart_customer_churn` | 1 row per `customer_unique_id` |
| `mart_revenue_monthly` | 1 row per month |
| `mart_seasonality` | 1 row per calendar month (all years combined) |
| `mart_buyer_type` | 1 row per buyer type (one-time vs repeat) |
| `mart_category_growth`, `mart_category_win_count` | 1 row per product category |
| `mart_review_churn` | 1 row per churn status |
| `mart_category_per_state` | 1 row per `customer_state`: its top category by gross margin (ties keep both) |
| `mart_revenue_per_state` | 1 row per `customer_state` |
| `mart_overview_kpi` | 1 row with the dashboard KPIs |
